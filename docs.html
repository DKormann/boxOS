boxOS client documentation

Protocol documentation for people and agents implementing boxOS clients.

Endpoints

  • POST /challenge: create a one-use proof-of-work challenge.
  • POST /proc: register, invoke, or inspect a procedure.
  • GET /stats: read current limits, prices, and resource usage.
  • GET /health: returns OK.
  • GET /example: interactive example client.
  • GET /client.js: browser ES module client.

JSON requests should use content-type: application/json. Procedure responses are JSON objects containing either ok or error.

The JSON API allows requests from any browser origin with Access-Control-Allow-Origin: *. It does not use cookies or credentialed CORS.

Client module

The hosted ES module handles hashing, proof of work, registration, and retries:

import { BoxOSClient } from "https://164.90.168.234/client.js";

const box = new BoxOSClient("https://164.90.168.234");
const counter = box.proc(`
  let count = +(ctx.load("count") || "0");
  count += 1;
  ctx.store("count", "" + count);
  return count;
`);

const result = await counter.invoke("my-shard", "", { fuel: 100 });

proc.invoke computes the procedure hash locally and attempts the invocation first. If the server reports that the procedure is unknown, the client registers the source and retries with a new proof. The server remains the authority for validation.

Lower-level methods are also available: hash, register, invokeHash, run, inspect, and stats.

1. Request a challenge

POST /challenge

{
  "challenge": "one-use UUID",
  "expiresAt": 1730000000000,
  "baseDifficultyBits": 8,
  "maxFuel": 100
}

A challenge expires after the duration reported by /stats. It is consumed by the first validation attempt, including a failed attempt.

2. Build the operation commitment

Commitments use literal newline characters:

  • Register: "register\n" + code
  • Invoke: "invoke\n" + shard + "\n" + hash + "\n" + arg
  • Inspect: "inspect\n" + key

3. Compute proof of work

Choose integer fuel from 1 through the current maxFuel. Find a non-negative safe-integer nonce such that:

input = JSON.stringify([challenge, fuel, commitment, nonce])
digest = SHA-256(UTF-8(input))
requiredLeadingZeroBits = baseDifficultyBits + ceil(log2(fuel))

The digest must begin with at least the required number of zero bits. Fuel therefore increases expected proof work approximately linearly.

4. Submit the operation

Register

POST /proc

{
  "register": "return arg;",
  "fuel": 1,
  "challenge": "...",
  "nonce": 123
}

{"ok":"SHA-256 source hash"}

The hash is lowercase hexadecimal SHA-256 of the exact UTF-8 procedure source. Registration consumes storage fuel, so larger procedures or a fuller server may require more requested fuel.

Invoke

POST /proc

{
  "invoke": "procedure hash",
  "shard": "client-selected shard id",
  "arg": "string argument",
  "fuel": 100,
  "challenge": "...",
  "nonce": 456
}

{"ok":"procedure result"}

The shard must contain 1 to 128 characters. Invocations on the same shard execute serially; different shards may execute in parallel. Worker creation consumes fuel according to /stats. Remaining fuel is a wall-clock execution budget. Storage writes consume additional fuel and shorten the deadline; deleting existing storage earns fuel.

Inspect

POST /proc

{
  "inspect": "procedure hash",
  "fuel": 1,
  "challenge": "...",
  "nonce": 789
}

{"ok":"stored procedure source"}

Inspection keys containing : are rejected. This prevents direct inspection of procedure-namespaced state.

Procedure runtime

The argument is available as arg. The ctx object provides:

  • ctx.store(key, value), ctx.load(key), ctx.delete(key), and ctx.has(key)
  • ctx.invoke(procedureHash, arg), which runs another procedure on the current shard
  • ctx.hash(proc) and ctx.validate(code)
  • ctx.string, ctx.number, ctx.boolean, ctx.record, ctx.struct, ctx.constant, and ctx.union

Keys and values passed to storage must be strings. Storage is namespaced by both shard and procedure hash, so different procedures on one shard do not share keys. Nested procedure calls remain on the current shard because ctx.invoke has no shard argument. Procedure source and namespaced state are persisted in SQLite across server restarts; challenges and active invocations are not persisted.

Limits and retry behavior

  • Read /stats rather than hard-coding limits or prices.
  • Invocations wait for their exclusive shard lock and an available worker while consuming fuel.
  • A lock-fuel response may be retried with a new challenge.
  • A consumed or expired challenge cannot be retried.
  • A timeout does not commit partial storage operations.
  • Proof of work is not authentication; the service is intentionally anonymous.

See capabilities.md in the source repository for the full security assumptions and limitations.
